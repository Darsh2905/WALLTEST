# Deviations from the proposal (and everything that is not literally in it)

The proposal (`WALLTEST_Project_Proposal_DB_Design.pdf`) is the source of truth. Every place where the implementation adds to it, strengthens it, or had to
differ is listed here with **what**, **why** and **which section**. Items marked ⚠ changed behaviour the proposal states; the rest are additive.
Nothing was silently diverged from: where something in the proposal could not work as written, the fix is implemented and logged here.

| # | What | Why | Proposal § |
|---|------|-----|-----------|
| D-01 | **Roles and logins.** Besides `high_side`, `low_side`, `audit_engine`, `compliance` (NOLOGIN) there is `walltest_owner` (owns every object, NOLOGIN) and two logins: `walltest_api` (NOINHERIT, no privileges of its own; every request runs `SET LOCAL ROLE <one of the four>`) and `walltest_lab` (used only by the Rules Lab). | A superuser or table owner bypasses RLS and would make the wall fake; the API must be a non-owner. Tests prove `walltest_api` owns nothing, cannot `SET ROLE` to the owner, and that `low_side` cannot read `upsi_item` through the API path. | 7, 8.4 |
| D-02 | **Denied attempts.** `access_event` gains `outcome` (`ALLOWED`/`DENIED`) and `detail` (reason: `NO_GRANT`, `CHANNEL_OFF`, `NO_ACTIVE_SLOT`, `WRONG_SIDE:…`). Gateway functions log a refusal **and return normally** with no rows. | Raising an error would roll back the very log row that records the attempt. Also, "logs show activity, not leakage" needs refusals visible (channel switched off = logged `DENIED`). | 8.3, 9 step 3 |
| D-03 | `audit_campaign` gains `clock_mode` (`LIVE`/`SIMULATED`) and `config jsonb` (seed, trust levels, design, channels, slot length). | The two clock modes must be recorded in the database (tamper-evident, labelled in the UI); the config makes every campaign reproducible. Partial unique index: at most one RUNNING campaign per wall. | 8.3 |
| D-04 ⚠ | **Commitment format.** `canary_slot` gains `committed_at`. The preimage uses start time in **microseconds** (the reference truncated to seconds) and is documented in `docs/COMMITMENT_FORMAT.md`. For LIVE campaigns the trigger overwrites `committed_at` with `clock_timestamp()` and requires it to precede the slot's start. | Commit-before-expose must be provable on the wall clock; live slots last 1–2 s. | 6.5, 8.4, 9 step 2 |
| D-05 | **Statistics beyond the proposal.** `audit_result` gains `p_adjusted` (Holm–Bonferroni across the (treatment × LOW agent) family), `acc_lower` and `leakage_bits_lower` (one-sided Clopper–Pearson at level α/K, valid simultaneously), `min_detectable_acc` (80% power at the cell's n), `family_size`, `alpha`, `clock_mode`. `p_value` stays the **raw** exact one-sided binomial p; `leakage_bits` stays the point estimate 1 − H(a). **The verdict uses the adjusted p.** | A point estimate is not a bound; 24 simultaneous tests inflate false alarms; "no evidence" must show what the test could not have detected. *Known limitation:* Holm can reject where the conservative Bonferroni-level bound is still ≤ 0.5, so `leakage_bits_lower` can read 0 for a LEAK cell that barely clears Holm. | 4(5), 6.3(8) |
| D-06 | **"Signed snapshots"** are implemented as a SHA-256 hash of the canonical field list (`audit_result.result_hash`, recomputed by `v_result_integrity`), not an asymmetric signature. | Tamper-evidence without key management; a DB superuser could still rewrite a row *and* its hash, so this is evidence against casual edits, not against the DB owner. | 6.3(8) |
| D-07 | `canary_variant` is also append-only; the `agent_note` logging trigger also logs `UPDATE` and `DELETE` (the proposal's `op` domain already contains them). `TRUNCATE` is blocked on every append-only table. | "Every write to shared memory is logged" includes edits; variants are evidence. | 6.3(9), 8.4 |
| D-08 ⚠ | **The wall trigger had two bypasses**, so the same rule is enforced on `wall_membership` (cannot add an agent with a UPSI grant to the LOW side) and on `data_asset` (cannot reclassify an asset as UPSI while a LOW agent holds it), as well as on `access_grant`. | Granting first and moving the agent behind the wall afterwards, or reclassifying afterwards, defeated the proposal's single trigger. Tests: `test_wall.py`. | 8.4 |
| D-09 ⚠ | **One audit clock per firm.** An extra exclusion constraint `EXCLUDE USING gist (slot_period WITH &&)` forbids overlapping slots across *different* campaigns, in addition to the per-campaign one. SIMULATED campaigns get disjoint 2-hour windows derived from their id. | `trade_order` has no campaign id (as designed), so a slot's score is "orders placed inside its window". Found by investigating a number that looked wrong: with two overlapping simulated campaigns, the price-only clean trader scored 0.30 instead of 0.5 because each campaign's orders were scored in the other's slots. After the fix the clean trader pools to 0.5 across 80,000 slots (see calibration). | 8.4 |
| D-10 | **No ANN index on `agent_note.embedding`**; nearest-neighbour search is an exact scan inside the slot window. The gateway scopes memory to the audit slot (only rows written since the slot opened are visible). | An HNSW/IVFFlat index with a post-filter on asset and time silently returns fewer rows than exist, so a real leak would be missed. Slot scoping keeps slots statistically independent. Embeddings are a deterministic hashed bag-of-words (384-d), computed in Python, searched by pgvector. | 7, 8.3 |
| D-11 | **Scoring predicates are written as `>= lower AND < upper`, not `<@`.** | A btree index on `placed_at`/`event_time` cannot serve range containment, so each slot's score scanned every order the agent ever placed: calibration throughput fell to about 30 slots/s and getting slower with history (ETA 46 min). With explicit bounds it ran at ~150 slots/s (200 campaigns in 29 s vs 309 s). Matters at the proposal's "millions of access-log rows". | 6.5 |
| D-12 | The **Rules Lab** login `walltest_lab` may `SET ROLE walltest_owner`, used only by fixed server-side scripts (no input reaches SQL) inside transactions that are always rolled back (tested: row counts before/after). | To show the trigger layer firing for the owner *after* the privilege layer already refused. The main API login has no such membership. | 8.4 |
| D-13 | **Sample-size table.** The proposal's 94 / 384 / 1,543 are reproduced exactly by the *normal approximation*. The exact binomial needs **95 / 386 / 1,551**, and the proposal's own n gives 77.3% / 79.5% / 79.6% exact power. The proposal's "1,500 slots … 55% at α = 0.001 with about 80% power" is **77.4% power** at 1,500 (minimum detectable accuracy 0.551). | The request was to recompute the table "from the exact binomial". Exact power is a sawtooth in n, so "exact n" is the first crossing. Both are shown side by side on the Power page. | 6.5 |
| D-14 | **Channels in 20 tables.** The three audited channels (notes table, vector memory, cache) are rows of the single `agent_note` table distinguished by `asset_id` → `data_asset` (`notes_table` TABLE, `vector_memory` VECTOR, `feature_cache` CACHE); the cache holds a derived sentiment feature. The shared channels are owned by a PUBLIC department (Technology Platform), so the grant review returns zero rows while information still flows: that is the point of the proposal. | The schema must have exactly 20 relations and no separate cache table is listed. | 6.1, 8 |
| D-15 | Minor domain additions: `app_user.user_role` also allows `DEAL_TEAM` (someone must create UPSI); `access_grant.valid_to` defaults to `'infinity'` (open-ended); `audit_campaign.status` ∈ PLANNED/RUNNING/CLOSED/ABORTED; `canary_slot` additionally requires a bounded half-open range, and a deferred constraint trigger enforces "offers 1:2" and "sealed by 1:1"; `treatment` has the composite uniqueness the composite FKs need. | The proposal lists the constraints but not these value sets. | 8.3–8.4 |
| D-16 | `high_side`'s RLS policy on `canary_variant` calls a `SECURITY DEFINER` helper (`wt_slot_opened`) and hides a slot's variants until it opens. | A policy subquery runs with the caller's rights; `high_side` has no privilege on `canary_slot` and the query failed with "permission denied" (caught by `test_roles_rls.py`). Also prevents pre-exposure. | 8.4 |
| D-17 | **Reveal timing.** `sealed_flip` is inserted at commit time (as workflow step 2 says) and hidden by RLS; "reveal" is the moment RLS lets `audit_engine` see it after the slot ends. Agents never read the flip: `gw_read_canary` returns only the selected variant's text. | Matches steps 2, 3 and 5. | 9 |
| D-18 | **Treatment cells.** `create_campaign` offers FULL_FACTORIAL (8 cells), ONE_AT_A_TIME (5), ALL_ON (1) and CUSTOM (each channel varied / fixed on / fixed off, via `create_campaign_cells`). Slots are assigned by balanced random blocking (each block of n_cells slots holds each cell once, order shuffled with the CSPRNG). `planned_slots` must be a multiple of the number of cells. The proposal's scope says "off one at a time only"; the full factorial is what the request and the attribution grid need, and one-at-a-time remains available. | Main effects need the factorial. | 4(6), 5 |
| D-19 | **Walls.** Besides the research/trading wall there is a second wall (research + only `trader-clean` on the LOW side) used by the null-control button. | The family and the scoring are defined over a wall's LOW agents; a null control needs a wall whose only LOW agent cannot leak. | 5 |
| D-20 | **Agents.** The research, leaky, partial and clean agents are scripted validation instruments with planted ground truth (accuracy = 0.5 + trust/2 when a signal is available). Expected accuracy is derived from the agents' logic and verified by tests (trust 1.0 → 16/16 and 40/40; trust 0 ⇒ leaky's orders equal clean's slot by slot). The optional LLM agent (stretch) is not required and was not used for any reported number. | The request. | 5 (scope) |
| D-21 | **LIVE engine robustness.** Commitments are published **3 slots ahead** (not 1); a reveal that the database refuses as too early (`WT006`) is **retried**, not fatal; a new LIVE campaign starts after the last committed slot of any campaign. | Found by the Playwright run: a 152-slot LIVE campaign was ABORTED at the very end because the engine decided "this slot has ended" from a one-off estimate of the DB clock offset (+30 ms) and, on a loaded machine, asked for the flip too early. The database (RLS) is the authority on "ended". The wider commit lead also tolerates a stall of ~2 slot lengths without violating commit-before-expose; the cost is that a cancelled run leaves up to 3 future slots committed (hence the start rule). Regression test: `test_live_run_survives_early_reveal_requests_and_commits_well_ahead`. | 9 steps 2, 5 |

## v2 (branch `v2`, migrations 012–016; methods and measurements in `docs/METHODS.md`)

Same rules as above. The schema still has exactly 20 tables; v2 only adds columns, functions, views, indexes and triggers.

| # | What | Why | Supersedes |
|---|------|-----|-----------|
| D-22 ⚠ | **Serial gatekeeping replaces flat Holm.** Per LOW agent, a pooled exact test over all its slots at α/n_agents is the gate; only if it rejects are that agent's cells and channels tested (Holm within the agent at α/n_agents). Every hypothesis has one globally adjusted p; FWER ≤ α over all of them under any dependence. `audit_result` gains `scope` (AGENT / CELL / CHANNEL), `channel`, `method`, `gate_passed`, `n_agents`, `log_e`, `acc_upper`, `leakage_bits_upper` and one row per hypothesis; `v_verdict` is now a lateral call of `campaign_inference()`. The v1 flat-Holm p stays visible as `p_adj_flat_holm`. | The headline question uses all slots (minimum detectable accuracy 0.622 instead of 0.918 at the demo default). Measured: weak leak detected in 49% vs 2.5% of campaigns; FWER 2.0% at α = 0.05 over 36 claims. | D-05 (family and verdict rule) |
| D-23 | **Channel attribution is a test.** Exact matched-pair sign test within randomised blocks (`CHANNEL` rows). | v1's main-effect bars were descriptive; the randomisation itself makes the sign test exact. | – |
| D-24 | **Two-sided bounds** (Clopper–Pearson upper bound and the matching bits bound). | "NO EVIDENCE" now says how much could leak at most. | D-05 (lower bound only) |
| D-25 ⚠ | **Sequential mode** (`config.inference = SEQUENTIAL`): mixture e-values (p = 1/E), confidence sequences, stop rules FIRST_LEAK / ALL_SETTLED (materiality) / MAX checked at block boundaries; `closed_at` is the exact stop boundary and `v_slot_score` ignores slots after it. FIXED stays the default and still forbids peeking; FIXED + an early-stop rule is refused. | Valid under continuous monitoring: false alarms 0.7% vs 13.3% for naive peeking on the same data. Honest cost: at a known effect size it needs more slots than a fixed-n test planned for it (median 88 vs 71). | the "no peeking" rule, for SEQUENTIAL campaigns only |
| D-26 ⚠ | **Per-agent logins.** Every agent has its own LOGIN role `wt_agent_<name>` (member of its side role, SET disallowed); gateway functions take no agent id; the v1 id-taking functions are renamed `wt_impl_*` and executable by no agent. Passwords are HMAC(master key file, role). | v1 limitation: a LOW agent could present another's id. A first v2 draft had the API login `SET ROLE` into agent roles; tests showed it authenticates nothing (PostgreSQL checks SET ROLE against the session user), so agents connect as themselves. The compose stack bind-mounts `./.keys` because roles are cluster-wide: every process provisioning them must derive the same passwords. | the per-side limitation |
| D-27 | **Signed evidence.** Merkle root (RFC 6962 domain separation) over every evidence row, format pinned to explicit column lists; inclusion proofs; Ed25519 signature over a canonical snapshot text, key outside the DB; the freeze re-hashes the rows it wrote and refuses unless they match the signed hash. Verified in the browser. | v1's "signature" was a hash a DB owner could recompute; now edits to any evidence row or verdict are detectable by anyone holding the published signature. | D-06 |
| D-28 | **Statistical kernels**: log-space incomplete beta (Lentz) + safeguarded Newton replace bisection over binomial sums; bisection versions kept as `*_bisect` references. | 15–33× faster bounds and MDA; accuracy checked against 60-digit mpmath. | – |
| D-29 | **Exact semantic search over distinct vectors** for compliance (`semantic_search`): `agent_note.embedding_canonical` (set by a BEFORE INSERT trigger), a covering partial index over representatives, an expression index on `embedding_key(embedding)`. **HNSW was measured and rejected** (recall@10 0.70–0.91, `scripts/index_studies.py`), and the gateway's vector search is now exact by construction (MATERIALIZED candidate set). | Restates D-10 with a measurement and adds a search that is fast without being approximate (14 ms vs 258 ms brute force, identical rows). | D-10 (reaffirmed) |
| D-30 | **Indexes for measured hot paths**; **BRIN measured and rejected** (lag analysis 2 → 68 ms) in favour of a B-tree on `access_event.event_time`; covering `(agent_id, isin, placed_at) INCLUDE (side, quantity)` replaces the scoring index. | `scripts/bench.py`, `scripts/index_studies.py`. | – |
| D-31 | **Engine**: sliding window of in-flight simulated slots, pipelined statements, NTP-style clock sync, top-N price reads, asynchronous commit for slot-phase transactions, campaigns left RUNNING by a dead process are aborted at startup. | Profiled and A/B-measured (+20% / +7%). Async commit cannot lose a verdict's data: the synchronous freeze flushes all earlier WAL, and unfrozen campaigns are aborted on restart (which also un-blocks their wall, a v1 gap). | – |
| D-32 | One v1 test (`test_blocked_channels_carry_nothing`) asserted a chance event (not 8/8 correct by momentum, p ≈ 1/256) and failed once in a full run; it now checks the deterministic claim (same decisions as the clean trader, zero allowed channel reads). | A test that can fail by chance proves nothing. | – |

## What is *not* implemented / known limitations
See the README section "Known limitations". In short: a PostgreSQL superuser can still disable triggers and rewrite rows, but no longer undetectably for frozen
campaigns (signed evidence root) unless they also hold the engine's signing key; SIMULATED campaigns cannot prove wall-clock ordering, and their gateway clock is a
session setting an agent with raw SQL could set (it cannot read flips; LIVE ignores the setting); the demo agents are scripted instruments, so the leak rates are
planted, not discovered; real UPSI and intraday data are out of scope as in the proposal.
